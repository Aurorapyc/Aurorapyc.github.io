搭一条 CI/CD 流水线：从代码提交到 Kubernetes 自动部署

发表于2026-10-07|更新于2026-10-07|运维实践

一、为什么做这个

工作里见得最多的场景是这样的：改了一行代码，然后要手动 docker build、手动 docker push、手动去服务器 docker pull 再重启。

改一次代码，重复一遍。累，而且容易漏。

这次的实验，就是把这条链路自动化：代码提交后，镜像自动构建、自动推送、自动部署。学名叫 CI/CD，说人话就是”不用手动敲那一串命令了”。

选了一个最小的应用，把注意力全放在流水线上。

二、整体链路

涉及的组件：

环节 用什么
应用 Python + Flask
容器化 Docker（多阶段构建）
持续集成 GitHub Actions
镜像仓库 GHCR（GitHub Container Registry）
容器编排 Kubernetes（minikube）

三、第一步：写应用

应用本身简单到只有二十行，就一个健康检查接口。

两个设计点值得说：

一是 host="0.0.0.0"，不能写成 127.0.0.1。

0.0.0.0 表示监听所有网卡，容器外才能访问；127.0.0.1 只能被容器内部访问。这个坑很多人第一次都会踩——容器起来了、日志也正常，但外面怎么都连不上，就是这里。

二是返回 host 字段（容器主机名）。

这样你 curl 的时候能确认请求真的进了容器；后面做负载均衡的时候，还能看到请求被分发到了哪个副本。

Docker 是按层缓存的。依赖很少变，代码经常变。把依赖层放前面，改代码的时候就只需要重建后面几层，不用重新装依赖——构建快很多。

多阶段的思路是：第一个阶段只负责装依赖（会产生很多中间文件），第二个阶段只把”装好的依赖”复制过来，中间文件不带进最终镜像。

实测对比：

版本 镜像大小
单阶段 207 MB
多阶段 191 MB

只小了 16 MB。因为基础镜像本身就大（python:3.11-slim 约 150 MB），而 Flask 依赖很小。多阶段在需要编译的场景（Go、C++）收益才明显。但方法得会。

五、第三步：手动推一次镜像到 GHCR

在交给自动化之前，先手动走一遍，理解每一步在干什么。

docker tag 并不是复制镜像，而是给同一个镜像再起了一个”带地址的名字”。推送的时候，Docker 看这个名字里的地址，决定送到哪里。

这里踩了第一个坑：GHCR 要求路径全小写。用户名里带大写字母，报错 repository name must be lowercase。

六、第四步：GitHub Actions 自动构建

这是整个实验的核心。在仓库里放一个工作流文件，GitHub 就会在指定事件发生时自动执行它。

逐段看：

  • on 是触发条件——push 到 main 分支时。
  • jobs 是要执行的任务。
  • runs-on 指定在什么环境跑（GitHub 提供的临时 Ubuntu 虚拟机）。
  • permissions 是给令牌的权限，packages: write 是推镜像所必需的。
  • steps 是具体步骤，顺序执行。

变量替换里有两个值得记：

${{ github.sha }} 是本次提交的哈希，用来当镜像版本标签——这样每个镜像都能对应到具体的代码版本。

${{ secrets.GITHUB_TOKEN }} 是 GitHub 每次运行自动生成的临时令牌。不用自己配，用完即弃，比存一个长期 token 安全。

这里踩了个大坑：permission_denied: write_package。

原因是我之前手动推了一个私有包，而 Actions 用的令牌是”另一个身份”，默认无权覆盖已有的包。最后删掉手动推的那个包，让 Actions 重新创建，问题才解决。

这个坑的本质是”私有资源 + 多身份”的权限归属问题——真实工作里很常见。

八、探针实验

为了真正理解探针，做了个破坏性实验：把应用的路由从 /healthz 改成 /health，但探针还访问 /healthz。

结果：探针 404，Kubernetes 判定应用不健康，反复重启 Pod。

两个探针的作用在这里就很直观了：

探针 失败时
livenessProbe（存活） 判定容器已死，重启它
readinessProbe（就绪） 判定未就绪，不再向它转发流量

实验完之后，把路由改回来、更新镜像版本。这时观察到了滚动更新：新 Pod 先启动并就绪，旧 Pod 才开始终止——全程服务不中断。

这一步是这次实验里印象最深的：原来”零停机部署”就是这么工作的。

九、踩过的坑

坑 原因 解决
docker build requires 1 argument 忘了最后的 .（构建上下文） 加上 .
容器外访问不到服务 监听写成了 127.0.0.1 改成 0.0.0.0
Permission denied (publickey) 用 SSH 地址但没配 key 换 HTTPS + token
Password authentication is not supported 输的是登录密码 用 Personal Access Token
repository name must be lowercase 用户名有大写 加一步转小写
permission_denied: write_package 私有包 + 身份冲突 删掉旧包重建

六个坑里，有三个其实是同一个原因：权限和身份没理清（大写、publickey、write_package）。当时是逐个试出来的，现在回头看，应该先想清楚”谁以什么身份在操作什么资源”。
