在阿里云 ECS 自建 Tailscale DERP：从美国中继到 20 ms

发表于2026-11-07|更新于2026-11-08|运维实践

一、我遇到的现象

我在外面的 Windows 上通过 Tailscale 访问家里 PVE 和内网 SSH。两台机器没打通 UDP 直连，tailscale ping 一直走美国 DERP：从 Windows 到 PVE 的往返延迟在 330 ms 到 1.23 s 之间。我手头有一台阿里云 ECS，就在上面搭一个离两端都近的中继。

位置 环境
国内中继 阿里云 ECS，Rocky Linux 9.x，约 1.6 GiB 内存，Docker Compose
家里 PVE，Tailscale 子网路由通往家里内网
外面 Windows，PowerShell，Tailscale
对外端口 12443/tcp 跑 DERP，3478/udp 跑 STUN

文中的域名和设备地址都已替换成示例。复现时把 derp.example.com 换成自己的域名。

二、先签证书，再启动容器

镜像 ghcr.io/yangchuansheng/derper:latest 拉取时报 not found，我最后固定到发布过的 v1.102.3。镜像的自签证书能让服务启动，但 Windows 和 PVE 都报过 x509: certificate signed by unknown authority，于是换成受信任的证书。

在 Cloudflare 建一条 A 记录指向 ECS 公网 IPv4，设为 仅 DNS（灰云）。普通 Cloudflare 代理不支持这里的 12443。创建一个仅能编辑该 DNS 区域的 API 令牌，写入 ECS 的 /etc/letsencrypt/cloudflare.ini：

目录和凭据用 root 管理，凭据权限设为 600。令牌、私钥和本地 certs/ 目录不提交到 Git。

用 Docker 运行 Certbot

ECS 上已有 Docker，直接用 Certbot 官方 Cloudflare 镜像 签发证书。DNS-01 验证由 Certbot 临时添加 TXT 记录，不需要开放 80 端口。

第一次输出 Account registered 后，Let’s Encrypt API 请求超时。没有生成证书，原命令重试后才看到 Successfully received certificate。临时容器退出会被删除，证书通过挂载保留在宿主机。

四、为什么中继一开，反而 SSH 不进家里

最开始我把故障说成了“SSH 连不上”，后来才分清：ECS 的公网 SSH 一直能连，断的是 Windows 经 Tailscale 到家里内网的 SSH。这两个连接要分别测。

netcheck 显示阿里云大约 7 ms，但这是探测结果。换完证书后，Windows 的 tailscale debug derp aliyun 已经能建立会话，Windows 到 PVE 却还是超时。PVE 的日志反复出现 derp.Recv: EOF；停掉容器后，它才切回官方中继，SSH 随之恢复。

最后定位问题的是 ECS 的容器日志：

证书已经修好，但 ECS 上的 tailscaled 查不到 PVE 的节点密钥，DERP 把实际客户端拒绝了。保留 DERP_VERIFY_CLIENTS=true，让 ECS 的 Tailscale 客户端能看到同一 Tailnet 的设备后，转发恢复。

保留客户端校验，检查 ECS 能看到哪些设备

挂载 tailscaled.sock 只是让容器可以查询宿主机上的 Tailscale 服务。开启 DERP_VERIFY_CLIENTS=true 后，ECS 上的 tailscaled 还必须能看到使用中继的设备。Tailscale 官方说明

在 ECS 的公网 SSH 窗口执行：

  • ECS 未登录：执行 sudo tailscale up，打开命令给出的链接，把 ECS 作为普通设备加入 PVE 和 Windows 所在的同一个 Tailnet。不需要启用出口节点或发布子网路由。
  • 已登录，但看不到 PVE 或 Windows：在 Tailscale 管理后台 → Machines 确认三台设备属于同一个 Tailnet、ECS 已通过设备审批（如果启用了审批），然后核对 ECS 登录的账号和访问策略是否让它看到这两台设备。
  • 两台都能看到，但日志仍显示拒绝：对照 ECS 的 tailscale version 和 DERP 镜像的构建版本。上游要求启用客户端校验时，derper 和宿主机的 tailscaled 从同一个 Git 修订构建。先核对版本和最新容器日志，保留客户端校验。

修复后在 Windows 上重测到 PVE 的 tailscale ping。出现 via DERP(aliyun) 才确认实际流量通过阿里云中继。

下次复现时，我会先保留 ECS 的公网 SSH 窗口，用 sudo docker compose logs --timestamps --tail=80 derper 查看日志。需要恢复访问就用 sudo docker compose stop derper，这样还能保留日志；down 会删除容器。

五、验证成功的样子

我最后看到三层验证都通过：

  • debug derp 建立 IPv4 DERP 会话，不再报 x509。没有配置 IPv6 和 80 端口，相关提示不妨碍这条 IPv4 会话。
  • 5 次 ping 全部显示 via DERP(aliyun)，往返延迟 20–22 ms。结尾仍然提示没有直连，因为数据确实经阿里云转发。
  • 内网 22 端口返回 TcpTestSucceeded : True，说明平时用的 SSH 路径也通了。

我后来查到家里路由器的 WAN 地址在 100.64.0.0/10，上游还有运营商 NAT。PVE 探测到 UPnP、映射没随目标 IP 变化，也不能据此判定是全锥形。现在验证了低延迟和连通性，没有测吞吐。

这次证书有效期到 2027-02-05，目前还没启用定时续期。后续可以用 cron 每天运行 Certbot 容器检查续期，再用 cmp -s 比较新旧证书和私钥的文件内容。只有文件变化时才部署；如果 DERP 正在运行，重启容器加载新证书，现有中继会话可能短暂中断。容器已经停止时，不需要把它启动。
